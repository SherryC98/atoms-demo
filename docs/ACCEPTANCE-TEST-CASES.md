# Atoms Demo 验收测试用例

> 版本：v1.0  
> 测试阶段：本地全量验收 → 部署后关键链路复查  
> 用例总数：20（8 个应用生成场景、7 个核心工作流、5 个异常/安全场景）

## 1. 需求与测试策略结论

Atoms Demo 的核心价值是通过智能体将自然语言需求转换为可运行、可交互的网页应用，因此产品本身适合采用 AI，评级为 **A**。

测试不适合全部依赖真实模型自动化。模型输出存在随机性，并会产生调用时长和 Token 成本，因此采用以下组合：

- 真实模型人工验收：验证不同应用类型、视觉效果和生成质量。
- 少量真实模型 E2E：守住最重要的交互主链路。
- API Mock E2E：稳定验证修复、失败和重试分支。
- 单元及集成测试：验证 HTML 校验、安全策略和限流逻辑。

## 2. 统一验收标准

### 2.1 测试环境

- 首先在本地环境执行全部 20 条用例。
- 本地全部通过后，才允许部署。
- 本地测试以最新版桌面 Chrome 为主。
- UC08 额外使用 `390px` 宽度的手机视口。
- 每个首次生成场景使用独立浏览器上下文，避免被系统识别为对已有项目的增量修改。

### 2.2 通过规则

- 确定性测试必须一次通过。
- 真实模型场景允许使用产品提供的“重试”一次，总耗时不得超过 150 秒。
- 同一真实模型用例连续两次失败，则判定不通过并保留原始错误。
- 不断言固定 DOM、具体 HTML 结构或像素级视觉效果，只验证用户可观察的行为和结果。
- 所有 P0、P1 用例均须通过；优先级仅用于安排执行顺序和部署后复查范围。

### 2.3 证据记录

每条用例至少记录：

- 实际 Prompt
- 开始时间与完成耗时
- 是否发生重试
- 实际结果与最终状态
- 页面截图或测试录像
- 浏览器 Console 和 Network 中的异常

## 6. 本地执行顺序

建议按以下顺序执行，以便先排除确定性问题，再消耗真实模型额度：

1. 执行现有单元测试、Lint 和生产构建。
2. 执行 UC19、UC20 等确定性安全测试。
3. 执行 UC16、UC17、UC18 等 API Mock 异常测试。
4. 执行 UC01、UC09、UC10、UC12、UC13、UC14、UC15 等核心链路。
5. 执行 UC02～UC08、UC11 等真实模型人工验收。
6. 汇总失败项；全部通过后才进入部署阶段。

## 7. 部署后复查

部署后只复查以下关键链路：

- UC01：首次生成与生成应用交互
- UC09：真实阶段顺序
- UC10：增量修改与旧功能保留
- UC13：刷新恢复
- UC14：Preview/Code 切换
- UC15：独立预览与权限隔离

不要在生产环境人为触发 UC20，以免污染真实配额或影响其他用户。

## 8. 已知边界与重点风险

### 8.1 生成应用的数据不跨刷新保存

生成应用运行在不含 `allow-same-origin` 的沙箱 iframe 中，不能使用 `localStorage`、`sessionStorage`、Cookie 或 IndexedDB。因此 UC13 刷新后只要求 Studio 项目和代码恢复，不要求生成应用内部的临时数据恢复。

### 8.2 独立预览不是公开分享

当前独立预览依赖同一浏览器中的匿名身份及 Supabase RLS。它适合“新窗口预览”，但其他用户或无痕窗口无权访问，不能按公开分享链接验收。

### 8.3 换风格后的错误重试需要重点验证

当前实现中，换风格操作没有更新 `lastSubmission`。如果换风格失败，页面上的“重试”可能执行此前的首次生成或增量修改，而不是重新换风格。UC16 必须覆盖这一分支。
