# 实现说明（WRITEUP）

本文档记录实现思路、关键取舍、当前完成度，以及若继续投入的扩展计划。不涉及笔试题原文，仅从工程实现角度说明。

## 1. 实现思路

整体是一条「计划 → 生成 → 校验 → （失败则修复一次）→ 落库 → 展示」的流水线，前端只负责编排调用顺序和展示阶段（`lib/agent-client.ts`），真正的业务逻辑都下沉到独立、可单测的纯函数模块：

- `lib/prompts.ts`：五个 prompt 构造函数（plan / build / edit / restyle / repair），职责单一，输入输出都是纯字符串，全部有单测。
- `lib/validate-html.ts`：LLM 输出不可信，必须过一层结构化校验和清洗，而不是简单的字符串正则替换。
- `lib/rate-limit.ts` + Supabase RPC：限流决策与原子计数分离，决策函数是纯函数、易测；原子性由数据库事务保证。
- `app/api/*`：四个 Route Handler 是"胶水层"，只做鉴权检查、调用纯函数、返回结果，不写业务逻辑。

前端状态机（`components/StageBar.tsx` 的 `Stage` 类型）贯穿组件与 API 编排层，保证"阶段"这个概念在 UI 和逻辑之间是同一份类型定义，不会出现前后端阶段名不一致。

## 2. 关键取舍

### 2.1 走 OpenAI 兼容网关的成本与安全取舍

- **为什么不直连模型官方 API**：密钥集中在网关侧管理、可审计调用量和内容、符合数据出境/合规要求，出问题时有统一的限流和熔断层，不需要每个业务方各自申请和保管官方密钥。
- **代价**：网关通常是官方 SDK 能力的子集——本项目在开发中就实测网关不支持 `temperature` 参数（见 commit `a6b5abe`），只能放弃精细调参，改为依赖 prompt 本身把输出约束住。网关的可用性、延迟也完全绑定在基础设施上，出故障时业务方无法绕过去。
- **应对**：`lib/llm.ts` 把网关调用封装成单一函数 `callLLM(prompt, system, maxTokens)`，一旦网关的接口协议变化或需要换供应商，只需改这一处。

### 2.2 CDN 白名单换质量

- 只允许 `cdnjs.cloudflare.com`、`cdn.jsdelivr.net`、`cdn.tailwindcss.com` 三个域名作为外部脚本/样式来源（`lib/validate-html.ts` 的 `WHITELIST`），其余一律在校验阶段拒绝（`errors` 里带上具体域名）。
- **取舍**：模型有时会想引用其他 CDN（例如某些小众图表库只在别的域名提供），白名单会让这类需求生成失败或被强制走修复循环，牺牲了一部分"模型自由发挥"的产出质量，换来的是可预测、可静态审计的外链攻击面——不需要在运行时才发现引入了恶意或不可控的第三方脚本。
- 即使校验漏判，运行时还有注入的 CSP（`script-src` 同样只放这三个域）兜底，双重保险。

### 2.3 阶段真实性 vs SSE 流式

- 当前 `planning → building → validating → (fixing) → done` 是按 HTTP 请求边界推进的离散阶段，每个阶段对应一次完整的 `fetch` 请求-响应，不是 token 级别的 SSE 流式输出。
- **为什么不做真流式**：真流式需要在生成阶段就把未校验、未清洗的中间产物暴露给用户（否则流式就没有意义），这与"用户看到的必须是过了安全校验的代码"这一硬约束冲突；同时会显著增加实现复杂度（需要流式转发网关的 SSE、前端增量渲染、以及流中途取消/重试的状态管理）。
- **代价**：单个阶段（尤其 build）如果耗时较长，用户看到的是一个静态的"Building"状态而非逐字增长的反馈，体感上不如逐 token 流式好。
- 阶段划分本身是真实的：每个阶段名对应一次真实发生的独立请求，不是为了好看而伪造的进度条。

### 2.4 创新点选型：换风格保留当前代码

- "换个风格"功能特意传入**当前代码**（`buildRestylePrompt(currentCode, need)`）而不是只传原始需求重新生成，这样可以保留用户在增量修改中已经加上的功能，只让模型调整视觉和布局。这是在"重新生成一遍"与"真正的差异化编辑"之间选择了后者，复杂度更高（prompt 要同时表达"保留功能"和"换视觉"两个约束）但用户体验更连续，不会因为换个风格就丢失之前的修改。

### 2.5 限流 fail-closed

- 限流通过 Supabase 的 `SECURITY DEFINER` RPC（`rl_incr`）做"先原子递增、再返回计数"，前端 `checkAndIncrement` 只要 RPC 报错、返回空、或返回数据形状不对（例如未认证），一律判定为拒绝，绝不在"看不清楚"的情况下放行。
- **取舍**：这意味着 Supabase 出现短暂抖动或网络问题时，正常用户也会被拒绝生成请求，牺牲了一部分可用性；换来的是杜绝"限流系统故障 = 无限调用网关"这种成本失控场景，这个取舍对一个会消耗真实 LLM 调用成本的系统是必要的。

## 3. 完成度

**已完成：**
- 匿名会话（复用优先，不无条件重新登录）+ Supabase RLS 隔离用户数据。
- 首次生成（plan → build → validate → repair 一次 → 二次失败即报错）全链路，落库后才置 `done`。
- 增量修改（保留已有功能）、换风格（携带当前代码）。
- 版本历史（消息表记录每轮 `code_snapshot`）+ 回到某一版（更新 `projects.current_version_id` 真实外键）。
- 校验：parse5 AST 解析、致命解析错误识别、结构检查（head/body）、外链白名单（只扫 `script[src]` 与 `link[rel=stylesheet]`）、CSP 注入（AST 级删旧插新，非字符串替换）、字节级大小限制。
- 限流：原子 RPC + 三级窗口（小时/日/全局）+ fail-closed，`rate_limits` 表无任何 RLS 策略防篡改。
- 三区 UI：聊天 + 折叠版本历史 + 预览（Preview/Code 切换），空态示例 prompt，阶段条，错误态 + 重试。
- 独立只读预览页 `/preview/[id]`，可新窗口打开分享。
- 纯逻辑模块（`validate-html` / `prompts` / `rate-limit`）的单元测试，共 20 个测试用例全绿。

**诚实说明未做的：**
- API Route Handler 层本身没有写自动化测试，只做了人工冒烟（浏览器 Network 面板 + console 观察），第 8 节要求的"自动测试范围"对这部分是用冒烟覆盖而非单测覆盖。
- 没有做真正的 SSE 流式输出（见 2.3 的取舍说明）。
- 没有做多人协作 / 分享编辑权限（预览页是只读的，编辑仍需回到本人会话）。
- 没有做用量看板或管理后台来查看限流/成本数据，目前限流数据只存在 `rate_limits` 表里，没有可视化。

## 4. 若继续投入：扩展计划与优先级

1. **（高优先级）补齐 API 层自动化测试**：用 Next.js Route Handler 的测试工具或简单的 fetch mock，覆盖限流拒绝、校验失败走修复、二次失败抛错三条关键路径，把目前的人工冒烟升级为回归可保障的自动化测试。
2. **（高优先级）真实使用量监控**：把 `rate_limits` 表的数据接一个简单的管理页面或定期导出，观察真实调用量是否接近阈值，为后续调整限流数值提供依据（目前的 20/100/500 是估算值，没有真实流量验证）。
3. **（中优先级）流式生成体验**：在保证"用户只看到校验通过代码"的前提下，探索"生成阶段展示模型的中间计划/进度文本流，但代码本体仍等校验通过后才整体展示"的折中方案，兼顾体感流畅和安全约束。
4. **（中优先级）账号体系**：从匿名会话升级为可选的邮箱/OAuth 登录，让用户换设备后仍能找回历史项目，同时保留匿名模式作为"免注册试用"入口。
5. **（低优先级）扩大 CDN 白名单的可控范围**：做一个后台可配置的白名单列表（而不是硬编码在 `validate-html.ts` 里），便于运营根据实际模型产出需要，安全地增加受信任的 CDN 域名。
6. **（低优先级）多设备实时同步预览**：当前 `/preview/[id]` 是每次手动刷新拉取最新代码，可以加一个 Supabase Realtime 订阅，编辑端保存后预览页自动刷新。
